## 0. 一句话

上一版按"一轮请求的先后顺序"切（组装→发送→触发），**切的是流程**；
这一版按"用户能改什么"切，**切的是能力面**：

| 模块 | 管什么 | 一句话判据 |
|---|---|---|
| **对话组装**（`llm_assemble`） | **推**给模型的东西 | 模型一进来就能看到的内容：谁说的、几点、引用了谁、群记录带不带、人格与规则怎么排 |
| **对话交互**（`llm_interact`） | 模型**能拉**的东西 | 给多少上下文、模型能不能自己查历史/展开消息/消解指代、图片要不要直接看、本地不够时补不补拉 |
| **对话发送**（`llm_deliver`） | 模型**吐出之后**怎么落地 | 一次发完还是逐句发；发几条、多长；怎么清洗；能不能不说；贴表情、戳一戳、拍一拍 |

**判据一句话：推 / 拉 / 发。** 三条之间不共享配置键，只共享"事实"（事件、历史、工具结果）。

## 0.1 设计自评（先看这一节，它会改动下面三处）

**结论：方向成立，但按初稿直接做，会有三个结构问题。** 已在本版修正，修正点标了 🛠。

| # | 判断 | 依据 | 处理 |
|---|---|---|---|
| 1 | **切割轴成立** | 三分法与代码里真实的三簇一一对应：组装=`PromptAssembler`/`sections`；交互=`prompt_prep` 的历史段 + `providers` + `tools/session_tools` + `llm_context`；发送=`delivery/*` + `llm_output` | 保留 |
| 2 | 🛠 **历史不能跨两块** | 初稿把"历史窗口/压缩"放交互、"行格式"放组装 → 同一个功能两个页面。按你自己的原话，"加多少历史"属于组装（控制消息怎么组装），"模型主动去取历史"属于交互 | **窗口/超限/压缩 → 组装；补拉/工具/跨会话 → 交互** |
| 3 | 🛠 **流式拆两个键是过度设计** | 拆成"请求模式 × 回复形态"后会得到 5 种组合（其中 1 种非法），比现在的 3 种更难懂——正好违背"开关要明确"。而且请求流式是实现细节，用户真正关心的是"回复怎么出" | **只保留发送的「回复形态」三选一；请求模式由框架按回复形态自动派生**；交互只留一个高级开关「强制非流式」（默认关，异常时才开） |
| 4 | 🛠 **交互模块没有机制落点** | 组装有 `assembly` 槽（`build`）、发送有 `output` 槽（`respond`），而交互是"配置域 + 工具源"，代码仍散在 `prompt_prep.py` 里 → 它会退化成一个配置页，然后框架代码继续各读各的键，"分散"换个地方回来 | **给交互一个契约方法 `plan(ctx) -> RequestPlan`**（框架每轮调一次），见 §2.1 |
| 5 | ⚠️ **最关键：三分法本身不能防"文案与机制打架"** | 真实的"不回"就是人格卡说"输出纯文本"、发言协议说"文本只是思考"——这是**文案与机制两处真值**。把插件切成三块，不会自动消除这类冲突 | 增加**能力事实表（CapabilityFacts）**：见 §4.5，组装只能按事实表渲染文案，禁止自己判断 |
| 6 | ⚠️ **附加能力的实现不能搬** | `send_poke` / `set_msg_emoji_like` 现在是 `llm_tools_extra` 的 175 工具执行器里带权限/冷却的实现，重写一遍必然漂移 | 发送**只做门控**（开关/频率/场景），实现复用工具层，见 §2.2 |
| 7 | ⚠️ **三分法不覆盖"什么时候说"** | 触发（主动/定时）与记忆不在三分法里 | 保留为独立模块，但**不得再自带一套"怎么说"的配置**（现在 `stream_proactive_enabled` 恒 False 就是重复真值的下场） |

**一句话：这版设计能不能成，取决于第 4 条（交互有没有方法）和第 5 条（能力事实表）。** 这两条不做，三分法只会把"配置分散"换成"代码分散"。

## 1. 边界判定表（有歧义的现象归哪边）

| 现象 | 归属 | 理由 |
|---|---|---|
| 本轮消息带不带时间、带不带"谁说的" | 组装 | 推过去的材料 |
| 引用/被 @ 怎么标（行内标签还是元信息块） | 组装 | 同上 |
| 群里有人戳了机器人/贴了表情，要不要记进 prompt | 组装 | 推过去的"互动事实" |
| 群聊环境记录带不带、带最近 50 条还是 60 分钟 | 组装 | 内容取舍 |
| 记忆/画像放 system 末尾还是 user 消息前面 | 组装 | 材料落位 |
| **给模型带几轮/几条历史、超了截断还是做摘要** | 组装 🛠 | 决定"模型看到什么"，属于组装（初稿放交互，已修） |
| 历史消息的行格式（单行 / 多行块） | 组装 | 材料渲染 |
| 请求用流式还是非流式 | **框架派生** 🛠 | 由发送的「回复形态」决定；交互只留"强制非流式"这一异常开关 |
| 本地历史不够时自不自动补拉 QQ 记录 | 交互 | 主动拉取 |
| 模型能不能调 `get_chat_history` / `search_history` / `expand_*` | 交互 | 模型可拉的能力 |
| "这条/那个人/这张图是什么意思"（展开与解释） | 交互 | 拉取 + 指代 |
| 指代消解（焦点表、预取、指代不明时怎么办） | 交互 | 拉取 + 语义补齐（产出的"焦点行"由组装渲染，见 §3.4） |
| 图片直接给模型看，还是只给 [图片] 占位 | 交互 | 多模态入参 |
| 一次发完 / 逐句流式 / 先想后发 | 发送 | 产出形态 |
| 一轮最多几条、单条多长、超了怎么处理 | 发送 | 产出约束 |
| 去 Markdown / 去括号动作 / 去 `[reply]` 残留 / 去汇报式复述 | 发送 | 内容加工 |
| 不说话是不是允许、被 @ 是否必须回 | 发送 | 产出策略 |
| 贴表情 / 戳一戳 / 拍一拍回应 | 发送 | 产出后的附加动作 |

**两处必须写明的分界**：

1. **"流式"这个词两侧含义不同**：请求的流式 = 逐 token 收回 / 一次收全（**实现细节，不暴露给用户**，由回复形态派生，见 §4）；回复的流式 = 逐句发 / 攒完一次发（**用户能改的点，归发送**）。初稿把它拆成两个键，属于过度设计，本版已改回"一个回复形态 + 框架派生"。
2. **"该不该说话"**：组装只提供**文案引导**（行为段里"什么时候不接话"）；发送负责**机制**（静默策略、被点名必回）。**文案与机制各管一头，且文案必须按能力事实表（§4.5）渲染，不互相读键。**

## 2. 三个模块的职责与代码归属

| 模块 | 拥有 | 从旧代码搬 | 明确不做 |
|---|---|---|---|
| **`llm_assemble`**<br>对话组装 | 段表与层、三套提示词方案、行为规则文案、人格落位、历史行渲染、**历史窗口与超限策略（截断/摘要）** 🛠、本轮消息标注、群聊环境记录、记忆块落位、媒体怎么标、请求落盘/打印 | `app/agent/assembly/*`（assembler / builtin_sections / prompt / presets / sections / layers / context_data / dump / **history_window / compress / compaction / context_budget**）、`llm_assembly`、`llm_message_meta`、`llm_enhance`、`group_log/context.py`、`session/model.py` 的行渲染 | 不选请求方式、不补拉历史、不清洗回复、不发送 |
| **`llm_interact`**<br>对话交互 | 请求模式（自动派生 + 强制非流式这一异常开关）、历史补拉、取历史/展开工具（`get_chat_history` / `search_history` / `expand_*`）、指代消解、图片是否内联给模型、私聊跨会话查询权限 | `llm_context/*`、`loop/prompt_prep.py` 的历史段、`tools/{history_search,session_tools,round_images}.py`、`media/image.py` | 不写提示词文案、不决定消息标注、不管回复形态、不管历史窗口大小 |
| **`llm_deliver`**<br>对话发送 | 回复形态（三选一）、条数/字数、超限处理、清洗、引用与 @ 落地、静默策略、节奏、**附加能力的门控**（表情/戳/拍）、唯一发送出口 | `llm_output/*`、`delivery/*`（output / speech / directives / channel / pool）、`loop/{assistant_output,chat}.py` 的产出与 flush；互动工具**沿用** `llm_tools_extra` 的实现，只加门控 | 不选请求方式、不拼提示词、不管触发 |

**留在别处的（不进这三块）**：`llm_memory`（记忆存储与召回）、`llm_tools_extra`（其余 OneBot/MCP 工具）、`llm_proactive`、`llm_schedule`（谁发起这一轮）。
它们**不属于三分法**，但必须复用三块的配置与唯一出口——从"用户能改的点"看，它们改的是"什么时候说 / 记什么"，不是"怎么说"。

### 2.1 每个模块必须有**一个契约方法**（否则它只是个配置页）🛠

| 模块 | 契约方法 | 框架何时调 | 落点 |
|---|---|---|---|
| 组装 | `build(req) -> list[dict]` | 每轮组 prompt 时 | 现成 `assembly` 槽（`controllers.py:210-227`） |
| 交互 | `plan(ctx) -> RequestPlan` | 取历史/装工具/定图片入参**之前**，每轮一次 | 新增 `runtime.interact` 句柄（与 `memory_service` 同级的文档化句柄） |
| 发送 | `respond(ctx) -> AsyncIterator[Message]` | 一轮产出回复时 | 现成 `output` 槽（`controllers.py:249-265`） |

```python
@dataclass(frozen=True)
class RequestPlan:
    history: HistorySpec          # 条数/轮数、超限策略（由组装给）、要补拉的条数
    tools: frozenset[str]         # 本轮允许的工具（含 expand_* / send_message / 互动工具）
    image_inline: bool            # 图片是否直接给模型看
    force_blocking: bool          # 高级开关：强制非流式
    reason: str                   # 一句话说明"为什么是这套参数"，进日志
```

`RequestPlan` 是**交互模块的唯一出口**：框架不再自己算历史条数、不再自己拼工具集，只问它一次。
这样"历史补拉/工具集/图片"这些散在 `prompt_prep.py` 里的判断才有唯一归属，否则三分法会在代码层重新碎掉。

### 2.2 附加能力只做门控，不重写实现 🛠

`send_poke` / `set_msg_emoji_like` 现在住在 `llm_tools_extra/src/onebot/`（带权限分级、冷却、审批）。
发送模块**只决定**"这几个工具本轮给不给 / 频率上限 / 哪些场景允许"，**不复制**执行器。
否则两份权限逻辑必然漂移——这正是现在 `onebot_tools_max_result` 读错来源那类 bug 的成因。

**跨模块不读键**：组装提供段表与 `register_section` 挂载点；交互/发送把自己的提示文案（未展开标记图例、发言协议、可贴表情标签）**注册成段**，由组装渲染。这样"提示词只由组装拼"，其余模块不碰 messages。

## 4. 关键解耦：一个「回复形态」，请求方式由它派生 🛠

现在的 `mode` 一个键同时决定"请求怎么发"和"回复怎么出"，是"开关说不清"的根源之一：
`mode=speech` 实际上等于"请求必须流式 + 回复必须先想后发 + 挂 send_message 工具"——三件事焊在一个键上。

**修正：不再暴露"请求模式"给用户**（初稿拆成两个键会得到 5 种组合、其中 1 种非法，比现在更难懂）。
只留**发送模块的「回复形态」**三选一，请求方式由框架按它自动派生：

| 回复形态（发送） | 框架自动选择的请求方式 | 用户看到的现象 | 什么时候选它 |
|---|---|---|---|
| **一次发完** | 非流式（可选流式） | 想完一次性发 1 条 | 小模型 / 不支持工具调用 / 想要稳定 |
| **逐句发** | 流式 | 边说边发，按句出气泡（现在的 `mode=stream`） | 想要打字感、长回复 |
| **先想后发** | 流式 + 工具（`send_message` / `finish`） | 先思考，轮次边界统一出气泡，可主动沉默（现在的 `mode=speech`） | 想要"想清楚再说 + 能分条 + 能不接话" |

- 交互模块只留一个**高级开关**：`force_blocking`（默认关，`showIf 回复形态 ≠ 先想后发`），
  description 写清"仅当流式输出异常或模型不支持流式时打开；打开后逐句发会变成整段收到后再按句发"。
- **非法组合不出现在 UI**：`先想后发 + 强制非流式` 由 `showIf` 隐藏，后端同时校验。
- 迁移：`mode=text → 一次发完`、`mode=stream → 逐句发`、`mode=speech → 先想后发`，行为一一对应。

## 4.5 能力事实表（CapabilityFacts）——防"文案与机制打架" 🛠

真实故障的成因不是"少写了一段提示词"，而是**同一件事有两处真值**：人格卡说"输出纯文本"，发言协议说"文本只是思考"。
三分法不会自动消除它，必须加一条硬约定：

```
发送/交互 每轮发布事实 → 组装 只能按事实表渲染文案
```

| 事实 | 谁发布 | 组装据此渲染 |
|---|---|---|
| `reply_form`（三种） | 发送 | 发言协议贴不贴、行为段写"文本即回复"还是"文本只是思考" |
| `silence_allowed` | 发送 | 行为段写"可以不接话"还是"必须回应" |
| `tools`（本轮可用工具集） | 交互 | "点名的工具必须存在"——工具没开就整句消失（这条现在已经是纪律，要升级成强制） |
| `emoji_ready` / `poke_ready` | 发送 | 【可用表情】【戳一戳】段与行为段对应行 |
| `expand_ready` | 交互 | 【未展开】标记语义段 |
| `image_inline` | 交互 | 媒体占位符 vs 看图指引 |

**纪律**：组装不得自己判断"有没有发言通道"，只能读事实表；任何"某段文案说了一件代码不会做的事"，用测试禁止（断言：协议类文案出现 ⇒ 对应事实为真）。

## 5. 框架侧改动（沿用上一版，去掉 TurnPlan）

上一版设计的全局 `TurnPlan` **不再需要**——三分法下每个概念都有唯一归属模块，框架只需按"域"取配置：

| # | 改动 | 说明 |
|---|---|---|
| 1 | `ConfigView` / `ChainedConfig` 修复 | 现在排在前的视图会吞掉后面模块的键（**已实测复现**），三个模块都会被短路 |
| 2 | 配置域改名 | `policy_get(runtime, "assemble"/"interact"/"deliver", key)` |
| 3 | 请求方式由回复形态派生 | `chat.py` / `output.py` / `turn.py` 不再各读 `stream_output`，统一从发送模块的 `reply_form` 派生；交互只提供 `force_blocking` 这个例外 |
| 4 | 唯一发送出口 | 主动/定时/chat 三条路径共用一条（pre_send/post_send/指令解析/msg_out/message_id 回填都在上面） |
| 5 | `turn.py` 补发言通道判定 | 非流式 + 先想后发 = 气泡丢弃且无日志（**现在的静默黑洞**） |
| 6 | 缺失能力必须 fail-loud | 模块没接管时明确降级 + 日志 + UI 红条，不允许静默丢能力 |

## 7. 实施（能并行的并行）

## 8. 验收（每键都要可观察）

1. **每个键一条"可观察差异"断言**：例如「时间行=off → 本轮 user 消息里不出现时间」「群记录=off → prompt 里没有【群聊记录】段」「回复形态=一次发完 → 一轮只产生 1 条 Message」「贴表情=关 → 工具集里没有 `set_msg_emoji_like`」。
2. **无效组合**：`请求=非流式 + 回复=先想后发` → UI 不出现该组合，后端拒绝并说明原因。
3. **静默必留痕**：任何路径没发出去 → 一行日志含 `source / 回复形态 / spoken=0 / 原因`。
4. **零僵尸键**：schema 键 = 归属表键 = 有真实读取点的键。
5. **降级可见**：任一模块被禁用 → 明确的 WARNING + UI 红条 + 就绪清单提示。
